# Shift 9 decision notes (working file; folded into DESIGN §19 at the end of the shift, then deleted)

- D74 manual ledger adjustments (D73 (1); DESIGN §7, D8): `ManualAdjustment.post` (core, sans-I/O) appends the audit row first and posts the ledger transaction with cause `MANUAL_ADJUSTMENT:<audit seq>` in the same transaction, so both exist or neither; an unexpected ledger answer (the cause exists) rolls back. Checked before any write: entries balance (LedgerChecks, §7.3 layer 1), note required (same rule as manual resolution), a named break must be the merchant's (else 404). `POST /v1/merchants/{m}/ledger/adjustments`, body `{"note","break_id"?,"entries":{"ACCOUNT":"signed amount"}}` (an object, since StrictJson has no arrays: one entry per account), new scope `ledger:adjust` (V9 widens `api_tokens_scopes_check`), ops tokens only (a merchant does not adjust its own books); the dev ops token gets it. 201 with audit_seq and cause; 400 unbalanced or malformed; 403; 404.
- D75 verify-audit (§7.6, §14): `core.audit.AuditChain.verify` walks the rows from seq 1: no gap, each prev_hash = the previous row's hash (GENESIS first), each hash = SHA-256 over prev hash + canonical entry. One-shot role `verify-audit` (prints rows and verdict, exits non-zero naming the first bad row); the same check is "audit chain intact" in `driftline verify`. Privileges (app role: no UPDATE/DELETE) and triggers (owner too) stop edits; the walk catches a superuser's edit with `session_replication_role = replica` (AuditTrailIT).
- CSV export (§14): a cell starting with `= + - @`, tab or CR gets a leading apostrophe and is quoted (OWASP CSV injection); a negative amount would therefore export as text, and the export has none.
- D76 webhook secret rotation (§10.2, §14; supersedes the secret half of D49's limit and of D73 (5)): `POST /v1/merchants/{m}/webhook-secrets/rotate` `{"kid","secret","overlap_seconds"?}` (scope `secrets:write`, added to V9 with `ledger:adjust`; ops tokens only). `PostgresDirectory.rotateWebhookSecret` in one transaction: a per-merchant advisory lock; refused while two secrets are active (IN_PROGRESS, 409) or if the key id was ever used (KID_TAKEN, 409); every active secret's window closes at now + overlap (1 min to 7 days, default 24 h); the new secret (32–512 bytes, encrypted with its row's context, D48) is active from now; an audit row WEBHOOK_SECRET_ROTATE (new kid, retired kids, retire time; never the secret) is appended through the store's own audit code on the same connection, so both commit together. The app role gets `UPDATE (active_to)` only, so a stored secret can be superseded but never rewritten. `MerchantRegistry.refreshSecrets` reloads active secrets (a merchant with a count other than 1–2 keeps its previous ones and is logged); `SecretRefresher` runs it every `driftline.secrets.refresh-interval` (30 s) and the endpoint once at once; the plaintext is wiped after encryption. New merchants still need a restart (D49). `Secrets.toString` no longer prints the AES keys.
- D77 personal data (§14 rows "Encrypted personal fields" and "Masked logs"): a gateway webhook may carry `"customer":{"vpa","phone","email"}` beside `"payment"` (payment events only). `wire.webhook.CustomerContact` validates and normalises each field (VPA `[a-z0-9._-]{2,64}@[a-z][a-z0-9]{1,31}`, a 10-digit Indian mobile with an optional +91, an email up to 254 characters; all lowercased); an invalid field is dropped and counted, never fatal; a malformed `customer` counts as none; `toString` prints no value. The contact travels beside the event (`IngestResult.Accepted.customer`), never in it: not in the canonical payload, its hash, Kafka, the core or the simulator, so dedupe and identity ignore it. Ingest stores it before publishing, in `payment_customers` (V10, append-only by trigger, app role SELECT and INSERT; first contact per payment wins) through `store.postgres.CustomerVault`, an app-only class like SettlementInbox (not a Store method: the sim has no personal data, so Store parity does not apply); a vault outage answers 503, so the gateway retries and nothing is published first. `app.pii.PiiCipher` encrypts each field with AES-256-GCM through SecretCipher under its own keyring (`driftline.pii.active-kid`, `keys`; kid in each ciphertext, so keys rotate), separate from the webhook-secret keys, with AAD `pii/<field>/<merchant>/<payment>` so a ciphertext moved to another row or column fails; the VPA's blind index is HMAC-SHA256 under `driftline.pii.index-key` over merchant and normalised VPA (no cross-merchant linking). No keys configured: storage is off, contacts are discarded (a warning at start-up), and search answers 503. Ops API: `GET /v1/payments/search?vpa=&merchantId=` (scope `breaks:read`; a merchant token searches its own merchant, an ops token one or all; up to 1,000 per merchant) and a masked `customer` on the payment timeline; no endpoint returns a contact in clear. Logs: every log message and stack trace goes through `PiiMasking` (first as Logback pattern converters; from D78 inside the JSON log encoder) (`ab***@okaxis`, `98******21`): a net under the rule that contacts are never logged; it can miss an unusual form. Evidence: CustomerContactTest, PiiCipherTest, PiiMaskingTest (the real logback file), IngestApiTest/OpsApiTest, CustomerVaultIT (ciphertext only, append-only, search, masked timeline, all captured app output clean). In Compose the sandbox adds a fake contact to every payment webhook (`FakeContacts`, a function of the payment id; the sim never does) and `scripts/pii-scan.sh`, run from the teardown of e2e.sh and chaos.sh, fails the run if a raw fake contact appears in any service's log, the Kafka topic or any table but the vault, or if the vault is empty. Not done: no retention or erasure of vault rows (a stated weakness for the README), and a contact that arrives only on a later webhook of the same payment is stored then, but a changed contact is not (first wins).
- D78 observability (§13): **Metrics.** Prometheus names exactly as §13 lists, from three places. (1) Counted where the work happens: `driftline_ingest_requests_total{route,status}` by a filter ahead of Spring Security (so 401/403 count; routes `webhook`, `order_event`, `settlement_file`; paths never become labels), `driftline_webhook_rejected_total{reason}` (bounded: `unknown_merchant`, `too_large`, `malformed`, `signature_<failure>`), and, in the partition driver's listener (`MatcherObserver`), `driftline_events_{consumed,duplicate,late}_total{source}`, `driftline_event_to_match_seconds` (ingest `receivedAt` to the commit that applied the event: every applied event, not only those that change a reconciliation status), `driftline_detection_lag_seconds{type}` (from the arrival of the record that raised the break, or for a timer-raised break of the newest record in that transaction, to the commit; a break a tick raises with no record is not measured), `driftline_consumer_lag_records{partition}` (`Consumer.currentLag`), `driftline_partition_fenced_total`, `driftline_subset_sum_ops` (the cost of each search run; a cached answer runs none); and in the dispatcher's listener `driftline_outbox_attempts_total{kind,result}` (`answered`, `no_reply`, `no_result`, `lost`). For these the core's `BatchOutcome` gained `fates` (offset → APPLIED, APPLIED_LATE, DUPLICATE, KEY_REUSED), `raisedBy` (break → offset of the record being applied when it was raised) and `solveOps` (`SubsetSum.solveCounted`, `BatchMatching.match` with an ops sink); `Resolver.Outcome` became a list of `Decision(breakId, state, enqueued command ids)`; all deterministic, so the simulator is unchanged (core 373 and sim 225 tests pass). (2) Read from the books (`store.postgres.BookStats`, one REPEATABLE READ snapshot; `BookMetrics` in the resolver role every `driftline.resolver.metrics-interval`, 15 s): `breaks_detected_total{type}`, `breaks_closed_total{type,how}` and `breaks_escalated_total{type,reason}` from append-only rows (reasons mapped to 12 bounded labels by prefix, else `other`), `breaks_open{type,state}` (adds `state` to §13's `{type}`, for the board's "by type and state"; open = DETECTED, AWAITING_EVIDENCE, ACTION_PENDING, ESCALATED), `deadline_headroom_seconds{type}` (earliest deadline among open planned breaks, negative once missed), `compensation_exposure_rupees` (what the open breaks would owe under the RBI rules if resolved now), `outbox_pending{kind}`, `outbox_oldest_pending_seconds` (from first send, or due time if never sent), `settlement_lines_total{result}` (`received` and each final status, so it only grows; statuses that can still change are the extra gauge `settlement_lines_unresolved{status}`), `pricing_drift_total` (short lines explained by fees that differ from the schedule), `watermark_lag_seconds{partition,source}` (gateway, merchant, and `bank` from the settlement watermark). Read from the database so they survive restarts and count every process's work once; every resolver instance reports the same values, so the board takes `max()`. **Traces.** The OpenTelemetry Java agent 2.33.1 is in the image (fetched with a SHA-256 checksum; off unless `OTEL_JAVAAGENT_ENABLED=true`; Kafka and JDBC instrumentation off), with manual spans on the OpenTelemetry API (a no-op without the agent: `Tracing.enabled()` is then false and no trace context is read or written). `ingest.webhook` (and `ingest.order_event`) is a child of the agent's server span and its own context is what the envelope carries (D46), instead of the caller's header; `matcher.batch` per chunk links to its records' traces (at most 128); `matcher.detect` is a child of the trace of the record that raised a break; `resolver.decide` a child of the break's context; `dispatcher.call` a child of the command's context, current while the HTTP client sends, so the agent's client span joins the trace. The resolver and dispatcher may be other processes, so contexts cross through `trace_contexts` (V11: subject `brk_…`/`cmd_…`, traceparent, append-only, app SELECT/INSERT), written after each driver's own commit: best effort (a lost row loses a trace, nothing else), not a Store method (the sim has no traces). A timer-raised break continues the `matcher.batch` trace, which links to the records, not the trace of the event that set the timer; commands the matcher enqueues itself (probes, sweeps) carry no context. **Logs** are one JSON object per line (`JsonLogEncoder`: timestamp, level, logger, thread, message, `trace_id`/`span_id` from the agent's MDC, error), with message and stack trace masked as D77 requires; the D77 pattern converters are gone. **Deploy:** `deploy/prometheus` (scrape by DNS of driftline, matcher, dispatcher on 9091; 4 alert rules: oldest pending command > 10 min, an open break with < 6 h headroom, a FEED_STALL open, consumer lag > 0 and rising for 10 min; each with a promtool unit test), `deploy/grafana` (provisioned datasource and a 26-panel board generated by `scripts/gen-grafana-dashboard.py`), `deploy/otel/collector.yaml`, Compose profile `obs` (collector 0.164.0, Jaeger 2.22.0, Prometheus v3.15.1, Grafana 13.3.0; pinned by digest; about 0.55 GB of caps, against §15.1's 0.50 GB estimate). Evidence: ObservabilityTest (metrics from every path; spans through an in-memory SDK; every metric the board and alerts query exists in a real Prometheus scrape, and a bogus name fails it), ObservabilityTablesIT (BookStats counts, append-only trace contexts), ObservabilityIT (real PostgreSQL and Kafka: a LATE_SUCCESS's spans from the webhook to the dispatcher's call share one trace; the scrape has the §13 metrics), `scripts/check-obs-config.sh` (CI job `obs-config`), and `OBS=1 scripts/e2e.sh` (CI's e2e job) with `scripts/obs-check.sh`: Prometheus targets up and rules loaded, Grafana board and datasource healthy, and a Jaeger trace (queried through Jaeger 2's `/api/v3`, the only query API it serves) in which `dispatcher.call` descends parent by parent from the agent's webhook server span through ingest.webhook, matcher.detect and resolver.decide, with the agent's HTTP client span under the call. The agent jar is read-only (`ADD --chmod=444`) in a directory created beforehand, since a directory `ADD` creates gets the same mode and the non-root user could not enter it (found by the first Compose run).
- D79 supply chain and the threat model (§14 "Dependency scanning in CI", "secret scanning", §16): **Lockfiles.** `dependencyLocking { lockAllConfigurations() }` in the Java convention plugin; a committed `gradle.lockfile` per module (and Gradle's `settings-gradle.lockfile`). A lockfile pins every resolved version, transitive ones included, and the build resolves exactly those: a bump of an explicitly versioned dependency fails resolution until the locks are rewritten, but a version a BOM manages (Spring Boot's) silently stays at its locked value, so `scripts/check-lockfiles.sh` (CI `security`) rewrites the locks and fails if anything changed; `--write` rewrites them after a version change (both behaviours were tried by hand before relying on them). **Scanners** (each run locally first, each shown able to fail): CI `security` runs gitleaks v8.30.1 over the whole git history (four findings in commit 87e00df, fake `whsec_…` test secrets later replaced, are accepted by fingerprint in `.gitleaksignore`; the history is public and is not rewritten; the only other hits are the git-ignored generated secrets of local runs), the lockfile check, and OSV-Scanner v2.7.0 over the module lockfiles through `scripts/osv-scan.sh`, which fails on any advisory whose highest CVSS score is 7.0 or more or which has no score, and prints every finding; CI `dependency-review` submits the Gradle dependency graph (gradle/actions dependency-submission) on pushes to main and pull requests, and runs dependency-review-action v5.0.0 (`fail-on-severity: high`) on pull requests (it can only be exercised on GitHub); nightly `trivy` (`.github/workflows/nightly.yml`) builds the app and sandbox images and fails on any fixable high or critical vulnerability with Trivy 0.76.1 (`scripts/trivy-scan.sh`; unfixed ones cannot be acted on, so they do not fail it; its cache is a Docker volume, so nothing root-owned lands in the tree). **What the first scans found, all fixed:** kafka-clients 4.2.2 brings lz4-java 1.11.2 (GHSA-mcr4-qmvw-px4g, 7.3; the producer compresses with lz4) and snappy-java 1.1.10.7 (two at 7.5): app constrains them to 1.11.4 and 1.1.10.12; Flyway brings Jackson 3.1.1 (several high) into store-postgres's integration tests: the Jackson BOM lifts it to 3.1.7; opentelemetry-api 1.62.0 (5.3): the OpenTelemetry BOM 1.67.0 in app, which is also the API the agent bundles (`TextMapGetter.keys` is deprecated there and now a default method, so `Tracing` no longer overrides it); the Temurin base image `21.0.12.1_1-jre-noble` has apt 2.8.3 (CVE-2026-109518, high, fixed 2.8.4ubuntu0.1): both images move to `21.0.13_9-jre-noble` (Java 21.0.13, apt fixed), five days old at the time, taken at once because it is a security fix. **Dependabot** (`.github/dependabot.yml`, valid against the schemastore schema): weekly, grouped, Gradle, GitHub Actions, the Dockerfiles and the Compose file, with a 14-day cooldown; a Gradle update whose lockfiles Dependabot leaves unchanged fails `security` until `scripts/check-lockfiles.sh --write` is pushed to its branch. **docs/THREAT_MODEL.md:** assets, trust boundaries, a STRIDE table whose every mitigation names its test or CI job (each name checked to exist; `CodecTest` gained cases for arrays, depth and duplicate keys, the strict-JSON limits it cites), the supply-chain controls, and the residual risks: no TLS or authentication inside the deployment (Kafka, PostgreSQL), no rate limiting, tokens revocable only in the database and without expiry, keys from the environment (no KMS), contacts kept forever, an unauthenticated management port inside the network, Grafana's anonymous viewer in Compose, the dev bootstrap file. Not in this phase: the `nightly` campaign and the full canary matrix of §16's `nightly.yml` (Shift 10, with the `nightly` profile), the kind smoke test (phase 5), and read-only root filesystems and NetworkPolicy (§14 "Extras", phase 5).
- D80 Kubernetes and container hardening (§15.3; §14 "Extras": non-root, read-only-root containers, NetworkPolicy): **Base** (`deploy/k8s/base`, kustomize): one Deployment per role (ingest with an HPA, 2 to 6 on CPU, and a PDB of minAvailable 1; matcher with 2 replicas, at most one per partition doing work, and a PDB of maxUnavailable 1; settlement worker, resolver and dispatcher with 1 each), the API Service, the `migrate` Job, a ConfigMap of everything not secret, and `secrets.example.yaml` listing each Secret's keys with no values (not in any kustomization). Every role runs one pod template: uid 10001, `runAsNonRoot`, RuntimeDefault seccomp, no service-account token, read-only root filesystem with an in-memory `/tmp` as the only writable path, no privilege escalation, all capabilities dropped, a memory limit, and startup, liveness and readiness probes on the management port. Both images now create user and group 10001 and run as `USER 10001:10001` (a numeric user, which Kubernetes needs to check `runAsNonRoot`), and Compose runs every Driftline and sandbox container `read_only` with a tmpfs `/tmp`, so the same constraints hold there. **NetworkPolicies:** default deny for ingress in the namespace; the API (8080) from anywhere; the management port (9091) only from namespaces labelled `driftline.io/monitoring=true`; egress is not restricted (the dispatcher's targets are wherever the gateway and the merchant are). Every resource carries `driftline.io/stage` (infra, migrate, app, verify) so a deployment applies them in order and waits between stages. **Overlay `kind`:** namespace `driftline`, dev-only PostgreSQL 17 and Kafka 4 (KRaft, one node; the controller voter is `localhost:9093`, since the Service exposes only 9092) StatefulSets on emptyDirs, the topic Job, the sandbox, the `verify` Job, policies letting only Driftline's pods reach PostgreSQL and Kafka (plus the topic job for Kafka) and anyone the sandbox (a dev-only fake the e2e suite drives from outside), Secrets generated from files `scripts/kind-smoke.sh` writes into the git-ignored `.dev/`, the API and the sandbox as NodePorts that `cluster.yaml` publishes on 127.0.0.1:18080 and :18085 (port-forwarding is fragile over a long suite), one ingest replica. Kind v0.33.0 with node v1.37.0 (pinned by digest): kind enforces NetworkPolicy since v0.24.0 (kube-network-policies). **`scripts/kind-smoke.sh`** (CI `nightly.yml` job `kind-smoke`; also on pull requests that change the manifests, the Dockerfiles, the script or the workflow; it needs about 5 GB, so it does not run on the 4 GB laptop, as §15.1 planned): builds, generates secrets, creates a fresh cluster, applies stage by stage, checks from an unlabelled pod that the API is reachable and PostgreSQL and Kafka are not, runs the e2e suite against the cluster (one scenario per break type, the manual resolution, the ingest security checks), runs `driftline verify` and requires it to succeed, and always saves every pod's log, checks it for raw customer contacts (D77) and deletes the cluster. **`scripts/check-k8s.sh`** (CI `ci.yml` job `k8s-manifests`): renders both trees, kubeconform v0.8.0 strict against Kubernetes 1.37, and asserts the hardening above on every Driftline and sandbox pod, the probes on every role, a default-deny policy, and no Secret in the base (a mutation that makes one role's root writable fails it). Locally the manifests were rendered and validated and the hardened images ran read-only through the Compose e2e and chaos runs; the kind smoke itself first runs in CI.
