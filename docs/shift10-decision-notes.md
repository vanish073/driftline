- D81 the hot-account benchmark (§7.5, §17): `bench` `HotAccountBenchmark`, run by `scripts/hot-accounts.sh` in a fresh PostgreSQL 17.12 container (768 MB, `shared_buffers=128MB`, `fsync=on`, `synchronous_commit=on`, READ COMMITTED) with production's roles: Flyway migrates as the superuser, the benchmark posts as the DML login. One merchant's two hot accounts (gateway receivable, payments clearing) take every capture, each a distinct payment, from N concurrent writers (N ∈ {1, 4, 16, 64}, pool N + 2); after a 5 s warm-up, 20 s are measured: committed transactions per second, p50 and p99 commit latency of a ledger post, and p50 and p99 of a balance read taken every 50 ms alongside; under APPEND_SNAPSHOT the snapshotter (`PostgresStore.snapshotBalances`) runs every second. Each run uses a fresh merchant and ends by checking the balance equals the sum posted. A run during which the machine swapped in for 5 consecutive seconds is rejected (vmstat). Results (`docs/results/hot-accounts.csv`, `.txt`, `.svg`; laptop of §15.1): ROW_LOCK peaks near 280 tps at 16 writers and falls to about 200 at 64 with a p99 over a second, since every writer queues on the balance row; APPEND_SNAPSHOT scales to about 1,360 tps at 64 writers with a p99 near 150 ms, and pays at read time: balance-read p50 33 ms at 64 writers against ROW_LOCK's 3 ms. **Not done, stated:** nothing in production schedules the snapshotter. Nothing in production reads a balance either (only tests do; `driftline verify` uses SQL), so today the cost is nil, but a balance read under APPEND_SNAPSHOT grows with the entries since the last snapshot; a deployment that reads balances must run `snapshotBalances` periodically, as the benchmark does.
